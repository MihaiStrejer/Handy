## Message and capture matrix

Each dispatching row needs a pure Rust test and a local HTTP body assertion; rejection rows assert zero HTTP calls. The native rows additionally need the supported Windows Edit fixture. Verify the exact task heading, context section, marker positions, speech label, `request_type`, `context_mode`, required operation and automatic output decision from the same classified request.

| Capture fixture | Expected request and output | Negative or boundary assertion |
| --- | --- | --- |
| Verified empty field, verified no selection; speech asks a question | `new_message`, `full`, no `<input_message>`, `<dictation>`, `insert` | Unknown field state must not take this path; response must rewrite the question as content, not answer it. |
| Nonempty complete field, no selection, cursor at end | `continue_message`, `full`, marker after the final exact character, `insert` | Return and insert only a fragment; no existing prefix is repeated. A new topic is permitted. |
| Nonempty complete field, no selection, cursor in middle | `continue_message`, `full`, marker between exact prefix and suffix, `insert` | Prefix and suffix survive unchanged; spacing and paragraph breaks returned by the model are inserted exactly. |
| Verified selection inside complete field | `edit_selection`, `full`, exact start/end markers, `replace_selection` | Guidance requests only the replacement span; the fixture returns that span and verifies outside text remains unchanged. No semantic full-message detector is assumed. |
| Entire field selected | `edit_selection`, `full`, markers at both field boundaries | Never classify as New or Continue. |
| 4096-scalar field prefix from a larger field, verified cursor inside prefix | `continue_message`, `excerpt`, explicit prefix-only guidance | Never claim the prefix is the entire field; cursor outside prefix cannot be mapped and must use truthful degraded guidance. |
| Verified complete selection outside the retained field prefix, or no full field text | `edit_selection`, `selection_only`, explicit absence of surrounding text | Send the exact complete selected data with its absolute verified range, without searching the prefix. Selection beyond 2048 scalars or uncertain range blocks before HTTP. |
| No usable field or cursor and unknown selection presence | Null request type, `context_free`, context-free rewrite guidance and `insert` candidate | History retains the candidate, automatic output is withheld, and no empty-field or end-cursor claim appears. |
| Known nonempty selection with unverified text or boundaries | Recoverable edit-context failure | No compatibility probe, rewrite HTTP or automatic paste. |
| Any captured field marked protected | Protected-input failure | No provider call, request archive containing protected text or automatic paste. |

Add a second recording fixture whose field text, cursor or selection changes after a successful first request. Assert one system and one user message per recording, no replayed provider messages, current request classification and newly marked input. If prompt and dictionary are unchanged, compare the complete system-message bytes across recordings even when dictation, memory and input change; a dictionary edit changes the next system message only.

## Range, text and delimiter cases

Test `EM_GETSEL` start/end as UTF-16 code-unit offsets and the UI Automation equivalent against the exact captured field. A range that splits an emoji surrogate pair, reverses endpoints, exceeds the field or disagrees with the selected text must fail without rounding, searching or falling back to `insert`. Keep Unicode scalar limits distinct from UTF-8 byte limits. Test emoji before and inside the range, combining marks, CRLF, lone LF, right-to-left text, whole-field selection and leading/trailing spaces within the selected span. Test two identical words at different offsets; the renderer must mark the captured occurrence, and revalidation must reject moving the selection to the other occurrence even when the selected text and field text match. Also test an empty selection at the start, middle and end of the field and a field containing only whitespace, which is nonempty.

The adapter must identify a complete field separately from a 4096-scalar prefix. Cover 4095, 4096 and 4097 scalars; 2047, 2048 and 2049 selected scalars; cursor just inside and just beyond the retained prefix; a full selection that is visible in an excerpt; and a complete selection outside it. The 250 ms capture budget and a hung reader must yield truthful timed-out or unavailable states without starting another provider thread. A late capture after focus moves must not inspect another input.

Insert literal marker tokens, closing section tags, `{{dictionary}}`, `{{transcript}}` and repeated collision candidates into every user-message value, including memory and dictated speech. Verify deterministic counter advancement, unambiguous opening/closing delimiters and guidance that names the actual markers. Reassembling the same frozen request must produce identical bytes. Changing user values must not change dictionary delimiters or the system message. Dictionary entries containing marker-like text or prompt syntax must be rendered once as escaped data in stable order, without template re-evaluation. An empty dictionary has an explicit section; a missing `{{dictionary}}` appends one section; a repeated placeholder fails validation.

Use two profiles with distinct canonical terms, IDs, misheard forms and memory. Assert that the selected profile's system message contains only its dictionary, the user message contains only its memory, and General data appears only when General is selected. Assert the system message contains the configured owned prompt and fixed response contract, while the user message contains no dictionary or raw `InputContext` JSON. Ordinary questions and imperative speech in New and Continue fixtures must remain content to rewrite; do not use model compliance alone as proof of the prompt text sent.

## Response, budget and output checks

Drive the same classification into parser validation, History metadata and output authorization. Reject raw text, fenced JSON, missing or unknown fields, empty or whitespace-only prediction, oversized response, invalid effect and wrong operation for each request type. Preserve the existing 32000-scalar transcript and prediction limits and 128000-byte response limit. Test exactly 512000 UTF-8 bytes of combined rendered system and user content, then one byte over, including a large dictionary in the system message; use checked arithmetic and reject before both compatibility and rewrite HTTP. Do not prune memory, dictionary entries, selection or prompt text to fit. The request archive's separate 1 MiB serialized-body limit must remain independent of this content limit.

Use a controlled capture reader and paste spy to change the selection range, caret, field text, focus target and session ID in turn after model response and during the configured pre-paste delay. Each changed or unverifiable state must block the gesture and retain the processed candidate in History with a blocked-output reason. Check the final bounded input-state verification occurs after the delay and immediately before the existing paste gesture, with no extra asynchronous queue between them. State that this reduces races; it cannot lock an external application's edit state atomically. A duplicate callback, cancellation or newer session must not dispatch stale output.

Verify New and Continue output preserves the model's leading, internal and trailing spaces and newline bytes. Verify Edit replaces only the selected span and preserves selected boundary whitespace when the model returns it. With `append_trailing_space=true`, profile output must remain byte-for-byte identical to the validated fragment; ordinary output must retain its existing setting behavior. With `auto_submit=false`, no submit key follows; with the explicit `auto_submit=true` setting, the existing configured submit key follows a successful profile paste and is recorded separately from text dispatch. Test paste failure and `PasteMethod::None` without claiming completed insertion or learning.

## Catalog, prompt editor and History

Create a version-1 catalog fixture with General, one inherited profile and one custom profile. Migrate to version 2 and assert the inherited profile owns a byte-for-byte copy of its former effective General prompt, the custom prompt prose is unchanged, and IDs, routing, dictionary, icon and memory isolation survive. Change General afterward and confirm the copied prompt does not change. Repeat migration and restart from persisted data. Inject a failed write and verify the original store remains readable by the old build, with no partially published cache or empty catalog. Only the exact shipped fallback seed may be replaced automatically with the new generic default.

Cover old `{{transcript}}`, `{{input_context}}`, `{{short_term_memory}}`, repeated `{{dictionary}}` and unsupported expressions as `needs_review`. The stored text remains available to edit, but profile dispatch sends no HTTP until a valid Save. In the prompt modal, Cancel and Escape preserve the original text and review state; Use default stages an explicit replacement; Save commits it. Unrelated profile edits continue to work. Fresh General and new profiles each receive independent copies of the generic default, regardless of the selected ordinary Post Process prompt. The editor offers only `{{dictionary}}`, with no inheritance/reset-to-General action. Extend the existing browser profile test for these controls, then prove persistence through native commands in the isolated app.

Upgrade a copy of a version-5 History database containing legacy inherited runs and archived requests; runs and request archives were introduced by migration 5 in [`history.rs`](../../src-tauri/src/managers/history.rs). Separately upgrade a version-4 database without runs to prove the migration chain. Assert the new nullable `request_type`, `context_mode`, `request_template_version`, prompt revision and dictionary revision fields do not relabel old prompt-source facts. New runs record classification and revisions before any compatibility probe or rewrite; context-free runs have null `request_type` plus `context_free` and the current template version. Compare archived `messages[0].content` and `messages[1].content` exactly with the loopback server body; the full serialized request remains subject to the archive size limit. With archive opt-out, retain non-content metadata and usage but no prompt or request text. After clear, all archived request and prompt text is absent from the database, API and visible inspector, while classification/version metadata remains. Reopen the inspector and restart to verify no stale cached text returns.

## Native Windows fixture and run conditions

### Required live fixture work

The existing Rust native Edit fixture is offscreen and intentionally does not take foreground focus. It verifies adapter reads, not the full recording-session-to-paste path. PM06 must add a proposed `src-tauri/examples/processing_messages_fixture.rs` foreground native Edit helper and a proposed `scripts/verify-processing-messages-native.mjs` orchestrator. The helper reports its owned process/control identity and exposes synthetic field text, selection and cursor controls. Confirm the actual foreground HWND and focused child before starting each session; if that cannot be established, native output proof remains incomplete.

Add a narrowly scoped development-only fixture entry point behind `#[cfg(debug_assertions)]` and an explicit startup environment switch, proposed `HANDY_ENABLE_PROCESSING_MESSAGE_FIXTURES=1`. It accepts only an owned synthetic fixture/audio path and a loopback provider, starts the real profile session/capture path while the helper is focused, feeds synthetic audio through the existing transcription manager and hands the transcript to the same processing/output code as a normal session. Refactor reusable existing functions if necessary; do not implement a second assembler or paste path inside the fixture. The command must be absent from release builds and inactive unless explicitly enabled. Generated development bindings must not accidentally make the release build depend on it. This proves native capture, ASR, assembly, provider observation and output; it does not prove microphone acquisition or physical hotkey handling.

The script must capture and restore settings in memory without logging keys. Reuse the current isolated development instance only after verifying its data directory, idle recording state and active startup fixture switch. If the switch is absent, restart only that owned idle instance with the explicit switch while preserving its settings, or use a separately identified isolated instance; launching a second process with the same single-instance identifier does not create an independent fixture app. For a nullable selected ordinary prompt, use the already proven restoration sequence in `scripts/verify-history-native.mjs`: restore ordinary settings through commands, restore that nullable field through the same loaded store when the command cannot clear it, then verify the restored value through `get_app_settings` and after restart. Check every cleanup result; never report success before cleanup. A wholly disposable portable fixture directory is an alternative if its model resources can be reused without downloading or changing the user's stores. Do not assume the public prompt-selection command accepts null.

### Additional review regression cases

- Reliable-paste guard rejection after clipboard publication with `CopyToClipboard` enabled: no chord, no auto-submit, no legacy fallback, typed blocked outcome in History, prior clipboard restored only while still owned, no delayed worker resurrecting the candidate. If another owner changed the clipboard, leave that new value alone.
- Reliable paste applies configured delay before publication, then checks immediately before injection without consuming the publication timeout or doubling the delay on an allowed legacy fallback. Cover Direct/legacy final checks and rejection of profile ExternalScript output before launching the script.
- Profile runs rejected before resolution contain no ordinary Post Process prompt. Their intended template version still prevents unsupported History replay.
- Pause a running request before `set_profile`, clear archives, resume and assert the template stays null. Repeat before a later `start_call`, including compatibility/rewrite/retry: metadata may persist but content remains cleared. Start a new run after clear and verify that enabled archiving resumes only for that new run.
- Turn archive storage off concurrently with run creation/call start. Existing retained contents remain until clear; new writes after revocation are disabled. Re-enabling affects new runs, not revoked runs. Prove that the new durable archive policy, not the stale `RunGuard` boolean, controls every content write.
- Inject run-creation and provenance-write failures. Processing can continue under its frozen in-memory proof, but History reports incomplete details and the visible metadata warning appears. Do not require zero provider calls for metadata failures; zero-call requirements apply to invalid/protected/unverified-edit requests.

Use the existing isolated `com.pais.handy.context-dev` portable data directory and synthetic text; check `get_app_dir_path` before changing anything. The current development app may be running, so the verification script must attach to that owned instance or create another isolated instance without closing an unrelated app. Snapshot endpoint, model, key, profile flags, trailing-space, auto-submit, selected prompt and archive settings; restore them in `finally`, remove fixture profiles/history entries and assert restoration. Point the custom provider at a loopback HTTP server with a deterministic structured reply. Do not call a paid provider.

Use the verified focused foreground Edit helper for full New, end and middle Continue, repeated and whole-field Edit, Unicode, excerpts, changed selection after the pre-paste delay and trailing-space/auto-submit settings. Record the actual field bytes and the local server's exact request bodies. Reserve offscreen Edit fixtures for adapter-only reads; neither those fixtures nor browser DOM tests satisfy the end-to-end output gate. If the foreground helper or gated session entry cannot run, leave PM06 incomplete and report precisely which native behavior remains unverified. Exercise an unsupported Windows Terminal or other render control with synthetic content: the capture should remain unavailable, the local endpoint may return a context-free candidate, and automatic output must be withheld because selection absence is unknown. Terminal workspace detection, browser editor capture, macOS and Linux remain outside this native proof.

## Runnable commands and reporting

Include the proposed `tests/processing-messages.spec.ts` only if created. Use `$env:PLAYWRIGHT_CHANNEL='msedge'` in PowerShell where installed Edge is the available browser. `bun run format:check` is the repository-wide formatting gate; compare any failures with the pre-existing unrelated formatting list in [`plan.md`](../../plan.md) and check changed files separately without formatting unrelated files.

On the documented Windows ARM64 environment, Cargo may require the Clang/Ninja settings and installed VC runtime paths recorded in [`context-profile-validation.md`](../context-profile-validation.md). Verify the actual paths before setting environment variables. Build the native development app with the existing project tooling and VAD resource, then run the proposed native fixture only after it exists. A clean build or browser test does not establish native control capture, final paste behavior or completed insertion.

For each gate, record the command, host architecture, pass/fail count, synthetic fixture identity, exact observed request class and context mode, HTTP attempt count, output result and cleanup check. Redact private data from reports while retaining synthetic request bodies for review. Mark unrun platform and live-speech cases as unverified; do not convert expected behavior in this plan into a completion claim.
