01 · What we built

Your original idea becomes an adapter around Handy’s existing voice pipeline. The profile owns routing rules, a system prompt, a long-term dictionary, and short-term memory. Audio transcription, the HTTP client, and text insertion remain Handy’s existing services.

P1 · CONFIGURE
Profiles UI → profile store

React edits a profile through Tauri commands. Rust validates, saves, and publishes the latest catalog.

P2 · CAPTURE & ROUTE
Focused app → frozen context

At the post-process shortcut: capture the destination, choose a profile, and resolve its prompt and dictionary.

P3 · TRANSCRIBE
Microphone → transcript

Existing audio, voice activity detection, and local speech recognition run alongside context capture.

P4 · ASSEMBLE & SEND
Context + transcript → endpoint

Two messages, one strict response contract, using the configured HTTP provider and model.

P5 · VALIDATE
Reply → accepted prediction

Check the response, current session, selection operation, and supported field state.

P6 · OUTPUT
Prediction → existing paste path

Check destination focus, then dispatch output through Handy’s configured paste method.

P7 · LEARN · PENDING
Confirmed output → profile update

The model can propose an effect. Applying it to dictionary or memory is still unimplemented.

VISIBLE THROUGHOUT

A “conversation” currently means separate voice sessions. There is no persistent model chat or server conversation ID. Every utterance sends a new system message and a new data envelope. Short-term memory is intended to carry corrections between requests, but its automatic writer is still missing.

04 · What actually goes to the model

P4 sends one system message + one user message to the existing /chat/completions client. The endpoint and model come from Post Process settings; a profile does not choose a different provider.

System role: instructions

Illustrative custom template:

Rewrite {{transcript}} using {{dictionary}}.
Use {{input_context}} for selected-text edits.
Respect {{short_term_memory}}.

Template variables become references to fields in the user message:

Rewrite [user data field: transcript] using [user data field: dictionary].
Use [user data field: input_context] for selected-text edits.
Respect [user data field: short_term_memory].

[Handy appends its fixed JSON response contract.]

Captured content is not interpolated into the system role or evaluated as template code. The fixed contract is abbreviated here. Template implementation · Assembly

User role: data

The example below follows the destination selected in the walkthrough. Values are synthetic; all four top-level fields are included even when the prompt omits their placeholders.

Native window/control handles remain private in Rust. An unavailable selection is explicit; it is not treated as a verified empty field. Character limits bound the transcript and captured field content.


P5 · Response: text + operation + effect
This is the current flattened JSON shape. The response parser rejects unknown fields, empty text, invalid action shapes, and a replacement operation without a verified selection.
An endpoint can propose add_misheard_form or remember instead of none. Those proposals currently remain in the session and are discarded on cleanup; they do not update the profile.
Current parser →


Compatibility is checked once per configuration
Enabling profiles is local: no model, API key, or network is required. The first profile-processing request for an endpoint configuration sends a small synthetic request requiring the strict response shape before sending captured context.
A successful check is remembered in this app process for the provider, URL, model, structured-output setting, and credential configuration. It contains no microphone or input-field data.
This cache remembers compatibility. It is not a warm system-prompt cache or a model conversation. Provider-side prompt caching is outside this implementation.
Providers advertising structured output receive a JSON schema. Other providers receive the same contract as instructions and must pass the same strict parser. Profile calls have a 60-second timeout; there is no plain-text fallback.

05 · What carries into the next utterance?


Survives app restart
On disk
  • Profile names, icons, application rules and prompt overrides.
  • General’s default prompt.
  • Canonical keywords and their misheard forms.
  • Existing Post Process settings and feature flags.
Profiles live in context-profiles.json; ordinary settings keep their existing store. Manual edits affect the next recording.


Until app exit
In the app process
  • Cached profile catalog for fast invocation.
  • Endpoint compatibility result.
  • Profile-scoped short-term memory store.
Memory caveat: read, remove, and clear exist. Production model feedback does not populate the store yet. Restart clears it.


One voice session
Frozen snapshot
  • Unique session identity and original destination.
  • Captured app, supported selection and surrounding text.
  • Chosen profile, effective prompt, dictionary and memory snapshot.
  • Prediction and proposed feedback effect.
Cleanup or cancellation releases the active session. Old results cannot attach to a newer recording. Provider/model settings are read when processing starts, rather than frozen with the profile.


The next request starts here
1 · Capture again
The focused destination may have changed. Choose the profile again.
2 · Snapshot current configuration
New manual dictionary or prompt edits now apply. Model proposals have not been saved.
3 · Send a new request
Fresh transcript + context + profile data. No prior chat messages are appended.
History is separate. Handy can save audio, the transcript, and final processed text through its existing history path. History is not injected as conversation memory, and a history entry is not evidence that paste completed. Profile-enabled history reprocessing is rejected because it has no original live target snapshot.

07 · One remaining architecture decision
Automatic learning needs a completion boundary. Border colours: green is settled, purple is decided by the team and still to be confirmed with the customer, orange is not resolved yet.
G1 · P7 · Open
What evidence allows a model proposal to update the profile?
The plan requires learning after a trustworthy completed text operation. Today the existing paste path confirms dispatch, and some output methods return before the destination changes. No feedback is applied yet. T07 decision gate


Paste dispatched
The operating system received an output action.
Missing: completion evidence
Did the intended field actually receive the intended result?
Apply learning
Validate the observed correction, then update the originating profile once.


G1-A
Verify the field changed · recommended
Read back a supported destination and check the expected result before learning. Pro: ties learning to the actual output. Con: adds verification work and leaves unsupported targets, including terminal input, without automatic learning.
G1-B
Ask for explicit confirmation
Let the user confirm a proposed learning action. Pro: can cover targets without reliable readback. Con: adds a new interaction and interrupts the flow.
G1-C
Accept successful dispatch
Learn after the existing paste call reports success. Pro: simplest integration and widest immediate coverage. Con: can learn even when the intended text never reaches the field; weakens the current completion requirement.


Answer: pending. Recommendation: G1-A. This page records no approval. You can reply with an option ID when you want to resolve T07.
After this decision, feedback still needs checks for an existing canonical keyword, evidence of the mishearing, duplicate/stale results, profile edits, and successful output. Parsing a model action alone does not provide those guarantees.



08 · What the evidence proves
Observed / recorded evidence
  • Fresh native captures above show the actual profile UI and recording icon, using synthetic data in an isolated development instance.
  • Recorded implementation verification: 295 Rust tests and 15 browser tests passed; frontend/native builds, lint, translation-key checks and clippy passed with existing warnings.
  • A previous native endpoint compatibility probe to the configured OpenAI model completed in 2,484 ms. This was a tiny synthetic contract check, not a voice-processing latency measurement.
  • Earlier native testing verified two profiles, dictionary and prompt persistence across an app restart, at 100% scaling.
Test results above are the recorded implementation results in plan.md, not suites rerun for this explainer. Verification record
Unverified or not implemented
  • Full live microphone → ASR → profile request → destination output has not been demonstrated end to end.
  • Automatic dictionary/memory learning and its inclusion in the next real request are unimplemented.
  • Native overlay fit at Windows 150% scaling and the user’s live review remain open.
  • Windows Terminal focused-tab workspace detection is deferred; terminal/browser/VS Code selected-text capture is unsupported.
  • New translation keys exist in all locales with English fallback text; translations remain pending.
  • Repository-wide formatting still reports existing failures; this page does not claim a clean whole-repo formatting gate.
