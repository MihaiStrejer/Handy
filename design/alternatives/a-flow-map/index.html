P1 · Before recording

Start Handy → load configuration

Managers and profile stores initialize. Saved profiles supply routing rules, prompts and dictionaries.

Configuration persists.
The profile selected in Settings is being edited; the next recording routes from its own captured destination.
Invocation

Invoke post-process recording

Requires post_process_enabled and post_process_profiles. Save the native target and create a unique session before showing the overlay.

This map follows profile mode.
Ordinary transcription and post-processing with profiles disabled use the existing path.
Cancellation applies throughout the active session. Cancel clears the session; late capture or response results cannot become a new session’s output. The queued paste callback checks cancellation again. Background work may still finish.

P2 · Context

Capture → route → freeze

Match the app, or fall back to General. Freeze its prompt, dictionary, memory and input context.

P3 · Audio

Record → stop → transcribe

Existing microphone, voice activity detection and speech recognition produce the transcript.

Both results meet at request assembly. Profile metadata also updates the recording widget.

App routing is available.
Terminal focused-tab workspace detection is deferred. Terminal, browser and VS Code selected-text capture is unsupported.

An empty transcript or failed transcription ends the path before the profile request.

P4 · Moment 2 · Request boundary

Send two messages in one fresh request

System role · instructions

Resolved rewrite prompt + strict response contract.

User role · JSON data

Transcript + dictionary + short-term memory + input context.

Reference data stays data. Native handles, session identity and profile authority stay local.

Use Handy’s configured HTTP endpoint and model after the compatibility check.

Protected field → no context request

A protected selection state blocks request assembly. Protected field content is not sent to the model.

P5 · Moment 3 · Response and field checks

Accept a prediction only if it passes

Parse the strict contract, match the operation to the captured selection, recheck supported field state, and confirm the session is still current.

{"text": "Codex", "operation": "insert",
 "effect": {"type": "none"}}

An effect may propose learning. Accepting a response does not apply that effect.

Invalid response → no output

Malformed JSON, extra fields, invalid effects, empty text or a mismatched operation are rejected. Request failures also stop output.

Changed field → no output

For supported native Edit capture, a changed selection, surrounding text or caret fails the pre-output recheck.

P6 · Output

Recheck focus → dispatch existing paste

The queued callback checks session identity, cancellation and the original destination. Accepted text uses Handy’s configured paste method.

A successful dispatch alone does not establish that the intended field received the text.

Moved focus → no output

On Windows, a different native window or focused control blocks insertion. The prediction is not redirected to the newly focused field.

P7 · Missing learning boundary

Automatic learning stops here

Paste dispatched→Completion evidence?→Profile update

No automatic dictionary or memory write is implemented. G1 chooses the evidence needed to permit it.

Before output ≠ after output.
The field recheck above detects edits during processing. It does not verify the result of paste.

↻ Next utterance: start a fresh request

Capture the current target and read the latest saved profile again. Saved configuration carries forward; prior request messages and uncommitted learning proposals do not form a continuing model conversation.

G1 · P7 · Open decision

What proves output completed before learning?

The proposed effect needs evidence that the intended text reached the intended field. These options are proposals; none is approved.

G1-ARecommended

Verify the field changed

Read back a supported destination and compare the expected result.

Gain: evidence tied to actual output.
Cost: more verification work; unsupported targets receive no automatic learning.

G1-B

Ask for confirmation

Let the user approve a proposed learning action.

Gain: can cover targets without readback.
Cost: adds an interruption and a new interaction.

G1-C

Accept successful dispatch

Learn when the existing paste call reports success.

Gain: simplest integration and broad coverage.
Cost: can learn despite failed insertion; weakens the completion requirement.

Answer: pending. Recommendation: G1-A. Learning still needs validation of the correction, originating profile, stale results and duplicate effects.
