Handy: from recording to output

Handy chooses a profile for the focused app, combines its instructions and vocabulary with your transcript, then checks the reply before sending text back to the original input.

Recording and context meet at the request

Starting a post-process recording begins two independent jobs: transcribing speech and identifying the profile and available input context. Both must finish before Handy sends the request. A profile is saved configuration; a session is one recording and its related work.

What survives the next recording?

One session ends. Its original destination and snapshot are released, so the next shortcut must look at the app and current configuration again.

On disk

Saved profiles and settings survive restart: app rules, prompts, manually edited dictionary and feature flags.

Until app exit

In-process state includes profile catalog, compatibility result and short-term memory store. Production model effects do not populate that memory yet.

This recording only

Session snapshot holds original destination, captured context, selected profile, prompt, dictionary and possible reply effect. Cleanup drops it.

Run two starts fresh

Handy captures the currently focused destination, chooses a profile again, snapshots its latest saved data, and sends a new two-message request if profile processing applies. The example’s “code desk” proposal is not added automatically to the next dictionary; manual dictionary edits still apply. No previous provider messages are appended. S8 S10

When audio saving succeeds, Handy may save history before dispatching output. A history entry does not prove insertion, and history is not replayed as a model conversation. History and output order.

G1. What evidence permits automatic learning?

The endpoint can propose an effect, but no automatic writer applies it. Consider a request that proposes remembering “use Codex.” Dispatch succeeds, but Handy has not read the destination back. Should the next request receive that correction?

G1-A · recommended

Read back the field

Verify expected text in a supported destination before learning.

Pro: ties learning to observed output. Con: needs readback work; unsupported targets such as terminal input cannot learn automatically.

G1-B

Ask the user

Ask for explicit confirmation of the proposed learning action.

Pro: works when field readback is unavailable. Con: interrupts the voice flow with a new interaction.

G1-C

Trust dispatch

Learn when the existing paste call reports success.

Pro: smallest implementation and broad immediate coverage. Con: can save a correction even if the field never received the text.

Answer: pending. Recommendation: G1-A, because it connects learning to a checked destination result. Correction identity, duplicate or stale delivery and profile-edit checks would still be required. Decision source S11
