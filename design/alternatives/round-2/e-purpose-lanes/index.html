Who hands off what, and why?

One recording has parallel audio and context work. Their results meet in a request with two different jobs: instructions tell the endpoint how to act; captured data tells it what to act on.

02

Why send two messages?

CURRENT · SYSTEM ROLE

Set the task and response contract

Handy renders the effective profile prompt into references to user fields, then appends its fixed JSON contract. This is where the endpoint learns how to interpret data and which response shape is valid.

effective prompt → field references
+ fixed text / operation / effect contract

Boundary purpose: dictionary, memory, captured context and transcript do not become instructions merely because they contain imperative text.

CURRENT · USER ROLE

Supply this utterance’s data

One JSON envelope contains all four fields, even if a prompt omits a placeholder. Dictionary and memory are reference data. Input context and transcript can change for every recording.

dictionary · short_term_memory
input_context · transcript

Handoff purpose: the endpoint gets enough context to rewrite the speech without receiving native destination handles or authority to choose a paste target.

Then: the endpoint returns text, operation and effect. The session validates the shape and captured selection, rechecks supported input, then output checks the original target before paste. An effect is only a proposal; no current writer saves it.
03

Stable parts, changing parts, and what exists

IMPLEMENTED TODAY

Separate authority; rebuild each request

Role and change frequency are separate: the dictionary stays user-role data even when unchanged; the system prompt can change with a profile or edit. Every profile request has a fresh system message and a fresh user data envelope. The chosen prompt, dictionary and memory are frozen for that session; the next session gets a new snapshot. No continuing model conversation is kept.

The app-process compatibility cache can skip a synthetic endpoint capability check for matching configuration. It does not cache prompts, tokens or conversations. Provider cache configuration and cached-usage monitoring are absent.

PROPOSED OPTIMIZATION · NOT IMPLEMENTED

Put repeatable reference data before variable data

Keep task instructions and a stable, versioned reference block in the earliest unchanged request prefix. Place changing input context and transcript after it. A dictionary edit would create a new version of that prefix.

Purpose: make repeated request prefixes possible for endpoints that support reuse. This is a design direction, not a claim that today’s dictionary has another role, that any provider has caching enabled, or that a cache hit or savings will occur.

Learning remains separate: the endpoint may propose a remembered correction or mishearing, but the effect stays in the session and is dropped at cleanup. The unresolved G1 completion choices remain G1-A read back the result, G1-B ask the user, or G1-C trust dispatch. None is approved or implemented here.
