1 Why freeze?

Settings or focus can change while speech is processed. The session uses the values and target captured for this utterance.

2 Why separate instructions from data?

Captured text and dictionary entries may contain arbitrary words. They stay reference data; the task and reply contract remain instructions.

3 Why stop before learning?

A model effect is only a proposal, and a paste call cannot prove the target field changed. A completion rule is still needed.

What crosses into the text endpoint?

Current boundary · Every utterance

The session builds and sends a fresh request

The system role gives the effective profile task, references to named data fields, and a strict reply contract. The user role carries the data. Both parts are sent on every request; there is no continuing model conversation or server conversation ID in this path.

System instructions

Task + field references + reply contract

+
User data envelope

Dictionary + memory + input context + transcript

system: "Rewrite [user data field: transcript] ..." + contract user: { dictionary, short_term_memory, input_context, transcript }

Why this boundary exists: prompt placeholders name data fields; they do not copy captured values into the instruction role. Native target handles stay local. A reply may suggest insert or replace_selection, but only a verified nonempty selection permits replacement.

Role and change frequency answer different questions. A dictionary can stay stable across utterances while remaining user-role reference data. A profile prompt can change while serving as system instructions. Role defines authority; content matching and endpoint behavior determine possible reuse.

Dictionary is in the user data envelope today, even though it may change less often than the transcript. Assembly · Template rendering · HTTP roles

Proposed boundary · Conditional reuse

Place reusable content before changing context

A future request shape could put stable instructions and stable reference data at the beginning, then add current input context and transcript. The reason is potential provider-side reuse of a matching prefix across requests.

Stable prefix, if unchangedTask + contract + stable reference data such as a dictionary revision
Changing suffixCurrent memory, app/input context and transcript

This is not an implemented cache. Stable reference data can remain in the user/data role; possible reuse does not require making it an instruction. A future ordering and serialization change needs a contract and trust review. The client currently sets no explicit prompt cache controls and records no prefix cache hit or cost measurement.

  • Reuse depends on a provider and endpoint that support it, plus a sufficiently identical eligible prefix. The system role alone guarantees nothing.
  • Profile or dictionary edits change that prefix. The request still sends the content each time.
  • Compute or cost savings are possible only if the provider actually reuses the prefix and reports a measurable result.

Different cache: Handy currently remembers whether a provider/model/key configuration passed a synthetic compatibility probe during this app process. That cache stores endpoint compatibility, not prompt content or model computation.

03

How does the system know it is safe to continue?

Each owner can establish a narrower fact. The output path checks those facts before dispatch. It does not inspect the destination after paste.

1 · Session currentUnique session ID and cancel generation still match.
2 · Reply validParser accepts bounded JSON, operation and effect shape.
3 · Input unchangedSupported field capture is rechecked; focus is checked before paste.
4 · Text arrived?No destination readback. This remains the learning boundary.

Current status: an accepted prediction can be dispatched. The proposed effect stays in the session and is dropped at cleanup; it does not update dictionary or memory.

Five visible stop paths · cause → consequence
Cancel before dispatch

Session or cancel check fails → old result does not paste. Already dispatched output cannot be undone.

Focus moves

Original target differs at paste time → output refused on Windows.

Field changes

Selection, surrounding text or caret differs on recheck → prediction rejected for supported capture.

Reply invalid

JSON, text, operation or effect fails parsing → no raw reply fallback and no insertion.

Protected input

Protected selection blocks assembly → no profile payload sent and no output from this path.

Native selected-text capture currently supports Windows Edit controls. Workspace capture is deferred; terminal, browser and VS Code selection capture is unavailable. Platforms without native target capture retain ordinary paste behavior. Guards · Session · Dispatch

The open learning decision

G1 · Open · No approval recorded

What evidence should allow a proposed correction to change the originating profile?

Concrete case: the endpoint proposes remembering a correction. Paste returns success, but the target field has not been read back. The system cannot yet say the correction appeared there.

G1-A · RecommendedRead back supported fieldsLearn only after the expected text is observed. Benefit: ties the write to arrival. Cost: unsupported targets cannot learn automatically.
G1-BAsk the userConfirm the proposed correction. Benefit: works without field readback. Cost: adds an interruption.
G1-CTrust successful dispatchLearn when paste returns success. Benefit: broad simple path. Cost: may learn when the target received nothing.
Answer: pending. Recommendation G1-A. A writer would still need correction validation, duplicate and stale-result handling, and profile write rules after this decision.

The page summarizes source code at baseline 8f9cf53 plus working-tree changes. Links open the repository files; the cited lines identify the relevant behavior. No screenshot or live voice run is claimed.

Limit of this evidence. Source inspection establishes implemented control flow and tests in source, not a complete observed microphone → endpoint → destination run. The proposed prefix has no cache controls or measurements in this implementation.
