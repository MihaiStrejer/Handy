P1 · What the saved profile contributes

1Choose a profile to edit

The highlighted “Architecture terminal” profile owns its rules, icon and vocabulary. Selecting it here chooses the editing target. Runtime routing uses the app focused when recording begins.

2Three views of the same profile

Context selection contains matching rules and prompt configuration. Long-term dictionary stores canonical words and mishearings. Short-term memory shows corrections for the running app process; the automatic writer is missing.

3Supply vocabulary as reference data

“Codex” is the canonical keyword; “codecks” and “code X” are misheard forms. The profile snapshot carries these entries into the user data message.

Settings → saved catalog → recording snapshot. Saving validates and persists the profile before publishing it for future recordings. General supplies the default prompt; a profile can inherit it or keep its own override. Storage · Inheritance

Match the app you actually speak into

The Context selection capture shows the executable rule that feeds P2. “Architecture terminal” matches WindowsTerminal.exe. General is the fallback if no rule matches or the best rules tie.

4Application executable: the runtime route compares this value with the captured app. Windows Terminal workspace detection is deferred; a window title does not establish the workspace.

5Save profile: the changed rule becomes available to the next recording after a successful save. The prompt editor is farther down this tab, outside this captured viewport.

03

P2 · What Handy can know about the destination

The app and its field are separate evidence

Handy can match Windows Terminal as an app while its selected text remains unavailable. Windows native Edit controls support selection and surrounding-text capture. General browser, terminal and VS Code selection capture is unsupported.

Captured fields state whether data is present, empty, unavailable, uncertain, protected or timed out. “Unavailable” cannot authorize replacing a selection. Native destination handles remain private in Rust. Capture · Session data

The widget reports the resolved profile

The session sends its identity, profile name, icon and input mode to the recording widget. It does not send raw selection text, the prompt or the dictionary.

Resolving the profile does not establish that the microphone is ready. Those operations proceed independently. Background capture and display event

Actual 256 × 50 native widget capture. The terminal icon occupies the far-left dot position; the exact profile name is in its tooltip. A synthetic session event produced this state. This is not microphone or completed-request evidence.

P4 · Why each request contains two messages

One message tells the endpoint how to work; the other carries what it should work on. This separates instructions from reference data. Message role does not say how often the content changes: a prompt can change, and a dictionary can remain identical across requests.

MESSAGE 1 · SYSTEM

Task and reply contract

The effective profile prompt supplies the rewrite task. Placeholders become references to fields in the data message; captured content is not interpolated into the instructions.

Rewrite [user data field: transcript]
using [user data field: dictionary].

+ Handy’s fixed response contract

Illustrative prompt, abbreviated contract. The contract requires a JSON object with text, operation and effect, and treats reference fields as untrusted data.

MESSAGE 2 · USER

Data for this utterance

dictionary
Canonical words and misheard forms from the selected profile.
short_term_memory
Stored correction text for that profile; automatic population is missing.
input_context
Captured app, supported field data and explicit availability.
transcript
The recognized words from this recording.

All four fields are sent even if the prompt omits their placeholders. This is a contract summary, not a captured request payload.

Assembly and parser · The HTTP client sends system followed by user.

Before real context is sent: check the endpoint’s contract

The first matching endpoint configuration receives a tiny synthetic request. It must return the expected structured reply before Handy sends this session’s context. A successful check is remembered for the current app process and matching provider, URL, model, structured-output flag and credential configuration.

This compatibility cache remembers the check result. It holds no continuing conversation or reusable model prompt. Requests use a 60-second timeout; endpoints that advertise structured output also receive a JSON schema. Compatibility and send behavior

Possible prefix reuse is a separate proposal

A provider might reuse an unchanged request prefix under its own conditions. Explicit prompt-cache controls and cached-usage measurement are absent here. Reordering stable data and measuring reuse would be additional work; this page establishes no cache hit, latency saving or cost saving. Request shape · Response model

05

P5–P6 · A reply must pass checks before output

The endpoint proposes text, operation and effect. Handy retains authority over the destination and session. An effect can propose remembering a correction or adding a mishearing; accepting its shape does not apply that change.

Before sending: protected input.
Request assembly detects a protected selection state.

The profile payload is not sent and this path produces no output. Guard

At the endpoint: failure or timeout.
The synthetic check or real request fails, or returns no content.

Processing fails; there is no transcript or raw-response fallback into paste. Request · Failure result

On reply: invalid or inconsistent output.
The parser checks shape, bounded text and effect, and operation against captured selection.

Reject the reply. Verified nonempty selection requires replacement; other accepted selection states require insertion. Parser

After reply: a supported field changed.
Recheck its selection, surrounding text and caret.

A mismatch blocks insertion. Unsupported fields have no equivalent content recheck. Input recheck

While waiting: cancellation or a newer session.
Check the session identity and cancellation generation before accepting and dispatching a result.

Stale results cannot produce new output. Cancellation cannot undo output already dispatched. Session · Dispatch guard

Before dispatch: the destination lost focus.
On Windows, compare the current destination with the original native target.

A changed target blocks output. Platforms without native target capture retain ordinary paste behavior. Target check · Paste call

Passing the checks permits dispatch. A successful paste call does not establish that the destination contains the expected text. This missing completion evidence is the reason G1 affects learning.

P7 · The connection that is still missing

G1 · Open · Learning after output

What counts as successful output before a proposed correction is remembered?

The endpoint can propose an effect, but no automatic writer applies it. Consider a request that proposes remembering “use Codex.” Dispatch succeeds, but Handy has not read the destination back. Should the next request receive that correction?

1 · Output dispatched

The paste call returns success.

2 · Completion unknown

Does the intended field contain the expected text? Current code has no readback here.

3 · Learning pending

The proposed correction is discarded with the session today.

Illustrative situation, supported by the dispatch path and session cleanup; no completed output is pictured.

G1-A · Recommended

Read back the result

Learn after supported fields contain the expected output.

Benefit: evidence that the text arrived.

Cost: verification work; unsupported targets cannot learn automatically.

G1-B

Ask the user

Let the user confirm the proposed learning action.

Benefit: covers targets without readback.

Cost: confirmation interrupts dictation.

G1-C

Trust dispatch

Learn when the existing paste call succeeds.

Benefit: broad coverage and simple implementation.

Cost: may learn when output did not arrive.

Answer: pending. Recommendation: G1-A, because it connects learning to observed output. No approval is recorded. A writer, semantic checks, duplicate and stale-result protection, and persistence still need implementation after this choice.
